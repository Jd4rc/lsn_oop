# Изучение ООП на Python

Репозиторий с учебными задачами и упражнениями для изучения объектно-ориентированного программирования (ООП) на Python.

Цель репозитория — освоить основные принципы ООП на практике, решать тренировочные задачи и развивать навыки написания чистого, понятного и поддерживаемого кода.

## Изучаемые темы

В процессе работы над проектом рассматриваются:

- классы и объекты;
- инкапсуляция;
- наследование;
- полиморфизм;
- композиция и агрегация;
- абстракция;
- свойства (`@property`);
- магические методы;
- итераторы;
- тестирование;
- статическая типизация.

## Реализованный функционал

Проект содержит классы `Product`, `Smartphone`, `LawnGrass` и `Category` для работы с товарами и категориями.

### Product

- создание объектов товара;
- валидация цены;
- подтверждение снижения цены пользователем;
- объединение одинаковых товаров через метод `new_product`;
- получение строкового представления объекта;
- вычисление общей стоимости товара (`цена × количество`);
- наличе подклассов `Smartphone`, `LawnGrass`
- поддержка магических методов:
  - `__str__`;
  - `__repr__`;
  - `__add__`.

### Category

- создание категорий товаров;
- подсчет общего количества категорий;
- подсчет общего количества товаров;
- добавление товаров в категорию(принимаются только объекты `Product` и его наследников, иначе вызывается `TypeError`);
- получение общего количества единиц товара через свойство `total_quantity`;
- вычисление средней стоимости товаров через свойство `middle_price`;
- поддержка итерации по товарам категории;
- поддержка магических методов:
  - `__len__`;
  - `__str__`.

Свойство `middle_price` вычисляет среднюю стоимость товаров в категории по формуле:

```
middle_price = total_cost / total_quantity
```

Если в категории отсутствуют товары или их общее количество равно нулю, свойство возвращает `0`.

### CategoryIterator

Реализован отдельный класс-итератор для последовательного перебора товаров категории с использованием протокола итерации Python.

### Order

- создание заказа на покупку товара;
- проверка, что передан объект `Product`;
- проверка корректности количества товара (количество должно быть больше нуля);
- вычисление общей стоимости заказа (`цена × количество`);
- выброс пользовательского исключения `InvalidQuantityError` при некорректном количестве;
- поддержка строкового представления объекта (`__str__`).

### PaymentProcessor

Для обработки различных способов оплаты реализована абстракция
`PaymentProcessor`.

Каждый способ оплаты представлен отдельным классом:

- `DebitPaymentProcessor` — обработка оплаты дебетовой картой;
- `CreditPaymentProcessor` — обработка оплаты кредитной картой;
- `PayPalPaymentProcessor` — обработка оплаты через PayPal.

Такой подход позволяет добавлять новые способы оплаты без изменения
существующих классов.

### Authorizer

Для проверки возможности проведения оплаты реализован абстрактный
класс `Authorizer`.

Доступны следующие реализации:

- `AuthorizerSMS` — авторизация посредством СМС-кода;
- `AuthorizerCaptcha` — авторизация посредством CAPTCHA.

Обработчики оплаты зависят от абстракции `Authorizer`, а конкретный
авторизатор передаётся в обработчик через конструктор.

Это позволяет заменять способ авторизации без изменения класса,
отвечающего за оплату.

## Применение принципов SOLID

В проекте на практике применяются принципы SOLID.

### Single Responsibility Principle

Классы разделены по ответственности:

- `Order` хранит данные заказа;
- классы `PaymentProcessor` отвечают за оплату;
- классы `Authorizer` отвечают за авторизацию.

### Open/Closed Principle

Новый способ оплаты можно добавить путём создания нового наследника
`PaymentProcessor`, не изменяя существующие обработчики.

Новый способ авторизации добавляется через наследование от
`Authorizer`.

### Liskov Substitution Principle

Объекты конкретных обработчиков оплаты могут использоваться вместо
абстрактного `PaymentProcessor`.

Объекты `AuthorizerSMS` и `AuthorizerCaptcha` могут использоваться
вместо `Authorizer`.

### Interface Segregation Principle

Классы зависят только от необходимых им методов интерфейса. Например,
обработчику оплаты достаточно метода `is_authorized()` — ему не нужно
знать, каким именно способом пользователь прошёл проверку.

### Dependency Inversion Principle

Классы обработки платежей зависят от абстракции `Authorizer`, а не от
конкретных классов `AuthorizerSMS` или `AuthorizerCaptcha`.

Конкретная реализация авторизатора передаётся через конструктор.

## Установка

Клонируйте репозиторий:

```bash
git clone <https://github.com/Jd4rc/lsn_oop.git>
cd lsn-oop
```

Установите зависимости:

```bash
poetry install --with develop
```

Активируйте виртуальное окружение:

```bash
poetry shell
```

## Тестирование

Запуск всех тестов:

```bash
poetry run pytest
```

Получение отчета о покрытии:

```bash
poetry run pytest --cov=src --cov-report=term-missing --cov-report=html
```

После выполнения команды HTML-отчет будет доступен по пути:

```text
htmlcov/index.html
```
